# 구현 검토 안내

## #7 내 아이디어 하나 저장·수정

작성 중 다른 사람의 생각을 보지 않고 자기 생각을 작성하는 기능이다. 진행자도 참가자이므로 같은 작성 API를 사용한다. 참가 키로 소유자를 찾으며, 요청에 수정할 아이디어 ID나 참가자 ID를 받지 않는다.

### 읽는 순서

1. `moasseugi-api.yml`의 Idea 계약을 읽는다. PUT은 저장·수정, GET `/ideas/me`는 내 아이디어 조회다. 저장 전 조회는 배열이나 빈 응답이 아니라 JSON `null`이다.
2. `idea/IdeaApiModels.java`와 `idea/IdeaController.java`를 읽는다. DTO는 요청·응답의 모양을 정하는 자료형이다. 요청은 `content`, 응답은 `id`와 `content`만 담는다. 컨트롤러는 HTTP 요청에서 안건 ID·참가 키·내용을 받아 서비스에 전달한다. `@NotBlank`와 `@Valid`는 공백뿐인 내용을 400으로 거부한다.
3. `idea/IdeaService.java`를 읽는다. 서비스는 저장 규칙을 담당한다. 안건이 있는지 확인하고 `CurrentParticipantService`로 키의 주인을 찾은 뒤, WRITING인지 확인한다. 그 참가자의 아이디어가 있으면 내용을 바꾸고 없으면 만든다. 조회에는 단계 제한이 없으며 자기 아이디어만 찾는다.
4. `idea/IdeaEntity.java`와 `idea/IdeaRepository.java`를 읽는다. 엔티티는 DB의 아이디어 한 행에 대응하고, 리포지토리는 행을 저장·조회한다. `participant_id`의 UNIQUE는 같은 참가자에게 두 행이 생기는 것을 DB에서도 막는다. 소속 안건은 참가자를 통해 찾는다.
5. `idea/IdeaControllerTest.java`를 읽는다. 실제 Spring 요청 처리와 H2를 사용해 응답뿐 아니라 저장된 행도 확인한다. 먼저 정상 흐름을 읽고 공백·키·없는 안건·작성 종료 후 수정 거부를 살펴본다.

Java 파일 경로의 기준은 `moasseugi-api/src/main/java/io/github/hjham0856/moasseugi/`이며 테스트는 대응하는 `src/test/java/` 아래에 있다.

### 저장 요청을 따라가기

`PUT 요청 → 입력 검증 → 키로 참가자 찾기 → 작성 단계 확인 → 그 참가자의 행 조회 → 새 행 저장 또는 기존 내용 수정 → {id, content} 응답`

`@Transactional`은 이 작업을 하나의 DB 작업 단위로 묶는다. 기존 엔티티의 내용을 바꾸면 JPA가 작업 종료 시 변경을 DB에 반영하므로 수정 분기에 별도의 `save()`가 없다. 처음 저장할 때는 `saveAndFlush()`로 DB 제약 위반을 서비스 안에서 확인한다.

동시 첫 저장으로 UNIQUE가 충돌하면 해당 제약 위반만 409로 응답한다. 실패한 트랜잭션 안에서 다시 조회하지 않는다. 사용자가 재요청하면 이미 생성된 자기 행을 수정한다.

### 검증 결과

2026-10-07 기준 `sh gradlew build`에서 기존 15개와 #7의 6개 테스트가 모두 통과했다. JSON null, 두 참가자의 기록 분리, 동일 ID 수정, 공백·잘못된 키·없는 안건·평가 단계 수정 거부를 확인했다. 별도의 DB 중복 삽입 검증에서 이름 있는 UNIQUE 제약 생성과 실제 Hibernate 예외의 제약 이름도 확인했다. 동시 HTTP 요청을 실행한 검증은 아니며, 실제 단계 전환 API와 화면·PostgreSQL은 아직 확인하지 않았다.

### 이후 연결

#7은 저장·조회 서버 기능까지다. 실제 화면의 입력 유지·저장 실패 안내는 #16에서 연결한다. #10의 실제 단계 전환 이후 작성 거부와 여러 브라우저 흐름은 M3에서 확인한다. 개발 DB는 H2이며 PostgreSQL 검증은 마지막 #19에서 수행한다.
