## #9 결과 분포·1회 채택

### 랜덤 UUID에는 순서가 없다 → 생성순은 따로 기록해야 한다
- 위치: `IdeaEntity.createdAt`, `IdeaRepository.findByParticipant_Session_IdOrderByCreatedAtAscIdAsc`
- 아이디어의 ID는 랜덤 UUID라서 ID로 정렬해도 만든 순서가 나오지 않는다. 결과를 "생성순"으로 보여주려면 생성 시각처럼 순서를 담은 값을 함께 저장해야 한다.
- 같은 시각에 두 행이 생기는 드문 경우를 위해 `id`를 두 번째 정렬 기준으로 붙여 결과 순서가 요청마다 흔들리지 않게 했다.

### 서로를 가리키는 외래 키(순환 FK)
- 위치: `SessionEntity.selectedIdea`(sessions → ideas), 기존 `ideas → participants → sessions`
- 안건은 채택 아이디어를, 아이디어는 (참가자를 거쳐) 안건을 가리킨다. 테이블 A를 만들 때 B가 아직 없으면 FK를 걸 수 없기 때문에, Hibernate는 테이블을 먼저 모두 만든 뒤 `ALTER TABLE … ADD CONSTRAINT`로 FK를 나중에 붙인다.
- 지울 때도 순서 문제가 생긴다. 채택된 안건이 남아 있으면 그 아이디어를 먼저 지울 수 없으므로, `ResultControllerTest`의 정리 코드는 `selected_idea_id`를 먼저 비운 뒤 행을 지운다.

### 지연 로딩(LAZY) 연관에서 ID만 꺼내기
- 위치: `SessionEntity.getSelectedIdeaId()`
- `@ManyToOne(fetch = LAZY)`는 연관 객체를 실제로 쓸 때까지 DB에서 읽지 않고 대리 객체(proxy)를 둔다. Hibernate의 proxy는 ID를 이미 알고 있어서 `getId()`만 부르면 추가 조회가 일어나지 않는다. 그래서 공개 안건 조회는 기존처럼 ID만 싸게 반환한다.
- 반대로 작성자 닉네임처럼 연관을 더 따라가야 하는 값은 트랜잭션 안(서비스 메서드)에서 읽어야 한다. 트랜잭션이 끝난 뒤 접근하면 `LazyInitializationException`이 난다.

### 집계를 DB에서 할까, Java에서 할까
- 위치: `ResultService.countByIdea`
- SQL `GROUP BY`로 개수만 받아오는 방법도 있지만, 회의 한 번의 평가는 많아야 수백 건이라 안건의 평가를 한 번에 읽어 Java에서 세는 쪽을 택했다. 쿼리 한 번, 코드가 단순하고 테스트로 확인하기 쉽다. 데이터가 커지면 DB 집계로 옮기는 것이 맞다.
- "평가 없음"을 0으로 채우는 처리는 어느 쪽이든 필요하다. 평가 행이 없는 아이디어는 집계 결과에 아예 나타나지 않기 때문이다.

### 확인 후 실행(check-then-act)의 경쟁 조건
- 위치: `ResultService.selectIdea`
- "이미 채택했는지 확인 → 채택"은 두 요청이 거의 동시에 들어오면 둘 다 확인을 통과할 수 있다. 진행자가 한 명이고 화면에서 요청 중 버튼을 잠그므로 현재 범위에서는 받아들인 제약이다.
- 엄밀히 막으려면 조건부 UPDATE(`… WHERE selected_idea_id IS NULL`의 영향 행 수 확인)나 낙관적 잠금(`@Version`)을 쓴다. 기존 평가 저장이 DB UNIQUE 위반을 409로 바꾸는 것과 같은 계열의 문제다.

## #15·#12 안건 생성·진입 화면

### 라우트 지연 로딩과 코드 분할
- 위치: `src/router/index.ts`의 `component: () => import('../views/…')`
- 화면 컴포넌트를 함수로 감싸 import하면 빌드 도구가 화면마다 별도 파일(청크)로 나누고, 그 주소에 처음 들어갈 때 내려받는다. QR로 들어오는 참가자는 홈·생성 화면 코드를 받지 않고 안건 화면만 받는다.

### 같은 화면이 재사용될 때: 라우트 파라미터 감시와 늦게 도착한 응답
- 위치: `SessionView.vue`의 `watch(sessionId, load, { immediate: true })`, `if (id === sessionId.value)`
- vue-router는 `/s/A`에서 `/s/B`로 이동하면 컴포넌트를 새로 만들지 않고 재사용한다. 그래서 `onMounted`만으로는 두 번째 안건을 불러오지 못하고, 파라미터를 감시해야 한다.
- 이전 안건의 응답이 늦게 도착해 새 안건 화면을 덮어쓰지 않도록, 응답을 반영하기 전에 "지금도 같은 안건인가"를 확인한다. 비동기 요청과 화면 상태를 연결할 때 반복해서 나오는 패턴이다.

### 디자인 토큰과 OKLCH
- 위치: `src/styles/tokens.css`
- 색·글꼴·간격을 CSS 사용자 정의 속성(`--color-ink`)으로 한 곳에 모으고 컴포넌트는 `var(--…)`로만 참조한다. 값 하나를 바꾸면 전체가 일관되게 바뀌고, 즉흥적인 색이 섞이는 것을 막는다.
- `oklch(밝기 채도 색상)`은 사람 눈의 밝기 감각에 맞춘 색 표기라서, 밝기(L) 숫자만 보고도 글자와 배경의 대비를 예측하기 쉽다. 그래서 강조색을 배경용 `--color-accent`와 글자용 `--color-accent-ink`(더 어두움)로 나눴다.

### Clipboard API는 "사용자의 실제 동작"과 보안 컨텍스트가 필요하다
- 위치: `SharePanel.vue`의 `navigator.clipboard.writeText`
- 브라우저는 클립보드 쓰기를 사용자가 직접 누른 클릭 같은 동작 안에서, 그리고 https나 localhost 같은 안전한 주소에서만 허용한다. 검토 중 스크립트로 버튼을 눌렀을 때는 실패했고 실제 클릭은 성공했다.
- 그래서 실패 시 주소 입력칸을 선택해 직접 복사하도록 안내하는 대체 경로가 필요하다. http로 된 사내망 주소에서 열면 실제로 이 경로를 타게 된다.

### 모바일 레이아웃의 작은 장치들
- `overflow-x: clip`: `hidden`과 달리 스크롤 컨테이너를 만들지 않아 `position: sticky` 등을 깨뜨리지 않으면서 가로 넘침을 자른다.
- `word-break: keep-all`: 한국어 문장을 글자 단위가 아니라 어절 단위로 줄바꿈해 읽기 좋게 한다. 긴 사용자 입력(제목)에는 `overflow-wrap: anywhere`를 함께 써서 화면 밖으로 나가지 않게 한다.
- `100dvh`: 모바일 브라우저 주소창이 나타났다 사라지며 바뀌는 실제 보이는 높이를 따른다(`100vh`는 주소창을 무시해 바닥글이 가려질 수 있다).
- `prefers-reduced-motion`: 운영체제에서 "동작 줄이기"를 켠 사용자에게는 애니메이션을 끈다. 홈의 "모" 조립 애니메이션이 여기에 해당한다.

## #11 핵심 규칙 통합 검증

### 기능별 테스트와 흐름(통합) 테스트의 역할 나누기
- 위치: `CoreFlowIntegrationTest`
- 기존 기능별 테스트는 단계를 빨리 만들려고 DB의 상태 값을 직접 바꾼 뒤 "평가 단계면 저장 거부"처럼 규칙 하나를 확인한다. 그래서 "전환 API가 실제로 바꾼 상태를 다른 API가 제대로 읽는가"라는 연결은 확인하지 못한다.
- 통합 테스트는 그 빈틈만 메운다. 규칙을 다시 검증하지 않고, 전환 API로 실제 단계를 넘긴 뒤 다른 API가 거부·허용하는지와 흐름 끝의 저장 결과만 본다. 같은 규칙을 두 번 테스트하지 않는 것이 TESTING.md의 원칙과 맞다.

### 응답에서 받은 값으로 다음 요청 잇기
- 테스트가 키 발급기를 가짜로 바꾸지 않고, 생성·참가 응답의 `participantToken`과 저장 응답의 `id`를 읽어 다음 요청에 넣는다. 실제 화면이 하는 일과 같은 순서라서 "응답 필드 이름이 바뀌었는데 테스트는 통과하는" 상황을 막는다.

### 저장 일관성은 행 수로 확인한다
- 평가를 바꿔도 새 행이 생기지 않아야 하므로, 끝에서 `COUNT(*)`와 `COUNT(DISTINCT 참가자, 아이디어)`가 같은지 본다. 화면이나 API 응답만 보면 "마지막 값이 보인다"는 것만 알 수 있고, 행이 중복으로 쌓였는지는 DB를 직접 봐야 안다.
- H2에서 `value`는 예약어라서 직접 SQL에서는 `"value"`처럼 따옴표로 감싸야 한다. 엔티티의 `@Column(name = "\"value\"")`도 같은 이유다. PostgreSQL 전환(#19) 때 다시 확인할 지점이다.

## #16 작성·평가 화면

### 폴링과 타이머 정리
- 위치: `SessionView.vue`의 `setInterval(() => poll(id), 3000)`, `onUnmounted(stopPolling)`
- 웹 페이지는 서버가 먼저 말을 걸 수 없으므로, 다른 브라우저(진행자)가 단계를 바꾼 것을 알려면 일정 간격으로 다시 물어봐야 한다. 이것이 폴링이다. WebSocket보다 단순하고 회의에서는 3초 지연이면 충분하다.
- 타이머는 화면을 떠나도 스스로 멈추지 않는다. 컴포넌트가 사라질 때(`onUnmounted`), 안건 링크가 바뀔 때, 마지막 단계(RESULT)에 닿았을 때 직접 멈춰야 요청이 계속 새어나가지 않는다.
- 이전 요청이 아직 끝나지 않았으면 이번 주기를 건너뛴다(`polling` 플래그). 서버가 느릴 때 요청이 겹겹이 쌓이는 것을 막는다.

### 서버가 확정한 값만 선택 상태로 보여주기
- 위치: `EvaluationPanel.vue`
- 클릭하자마자 선택된 것처럼 보여주는 방식(낙관적 표시)은 빠르지만, 저장이 실패하면 사용자는 평가가 기록됐다고 믿게 된다. 평가는 결과 분포에 그대로 들어가므로, 서버 응답의 값(`response.value`)이나 불러온 `myEvaluation`만 선택으로 표시한다.
- 검토 중 저장 요청을 강제로 실패시켜 보니, 아무것도 선택되지 않은 채 오류 문구가 나오고 다시 고를 수 있었다.

### 항목별 저장 중 잠금으로 요청 순서 문제 피하기
- 같은 항목에서 "좋음 → 별로"를 빠르게 누르면 두 요청이 동시에 날아가고, 응답이 거꾸로 도착하면 화면과 서버가 서로 다른 값을 가질 수 있다. 저장 중인 항목의 버튼만 잠가 한 항목에는 요청이 하나씩만 가게 했다. 다른 항목은 계속 누를 수 있다.

### 저장 중에 더 입력한 내용 지키기
- 위치: `WritingPanel.vue`의 `if (text.value === submitted)`
- 저장 요청을 보낸 뒤 응답이 오기 전에 사용자가 더 입력할 수 있다. 응답으로 입력칸을 무조건 덮어쓰면 그 입력이 사라지므로, 보낸 내용과 지금 내용이 같을 때만 응답으로 맞추고 다르면 "아직 저장하지 않았습니다"로 남긴다.

### 되돌릴 수 없는 행동에만 확인 단계 두기
- 단계 전환은 되돌릴 수 없어서 첫 클릭은 경고와 확인/취소만 보여주고, 확인을 눌러야 요청을 보낸다. 반대로 평가 선택처럼 바로 다시 바꿀 수 있는 행동에는 확인을 두지 않는다. 확인창이 잦으면 사람들은 읽지 않고 누르게 된다.
